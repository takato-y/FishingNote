## 背景

バックアップ（REQ-017）には、釣り場を含む全データが入る。保存先には、利用者が選んだクラウドの保存場所も含まれる。
暗号化しない JSON では、ファイルを手に入れた人が誰でも中身を読める。

Android には、端末の中に鍵を置く鍵保管庫（Android Keystore）がある。
しかし、バックアップは機種変更や紛失のときに、別の端末へ戻すための物である。

## 決定

- バックアップの暗号化の鍵は、端末の鍵保管庫に置かず、利用者のパスワードから作る
- 鍵の作り方は PBKDF2（HMAC-SHA256、繰り返し 600,000 回、毎回ランダムな16バイトの塩）、暗号は AES-256-GCM とする。形式名・版・繰り返し回数も認証の対象に含める
- 読み込むときは、繰り返し回数が 100,000〜2,000,000 の物だけを受け付け、中身の大きさも鍵を作る前に確かめる
- パスワードは半角の英数字と記号だけで12文字以上とする。よく使われる物・よくある言葉に数字や記号を足した・置き換えた・くり返しただけの物・文字の種類が5種類未満の物などは、規則で断る
- 自分で決めたパスワードは、さらに強さの見積もり（zxcvbn4j）で一番上の段階（推測に 10^10 回以上かかる見込み）に届かない物を断る。見積もれなかったときも断る
- 保存の画面では、アプリが作るパスワード（見間違えやすい文字を除いた57種類の文字を16個、4文字ずつハイフンでつないだ19文字。約93ビット）を、おすすめとして先に出す。作ったパスワードは規則だけで確かめる
- 「パスワードで守る」は保存のたびに選べ、最初はオンにする

## 理由

- 端末の中の鍵は、端末と一緒に失われる。機種変更や紛失のときに戻せないのでは、バックアップの目的を果たせない
- バックアップのファイルは、手に入れた人が端末の外で時間をかけて試せる。繰り返し回数を増やしても弱いパスワードは補えないため、パスワードそのものに強さを求める
- 全角・半角カナ・濁点の分かれた形などは、端末の入力の設定で見た目が同じでも別の文字になる。半角に限れば、どの端末でも同じ鍵になり、機種変更の後に「パスワードが違う」とならない
- 人が考えたパスワードは、規則と見積もりを通っても推測されることがある。アプリが作った物を先に勧めれば、推測されにくいパスワードを選びやすい
- 作ったパスワードはランダムなので見積もりは要らない。規則だけで確かめれば、見積もりが使えない端末でも作って保存できる

## 影響

- パスワードを忘れると、そのバックアップは戻せない。保存の画面にその旨を書き、作ったパスワードは紙などに書き写し、ファイルと別の場所にしまうよう知らせる
- 暗号化・復号ともに、端末（エミュレータ）で約2秒かかる。性能の低い端末では長くなるため、保存中と確かめ中はその旨を表示する
- 暗号化に入る道は保存の確認の窓の1つだけで、暗号化の直前は規則だけで確かめる。別の入口を足すときは、画面と同じ判定（規則と見積もり）を必ず通す
- 読み込みではパスワードの規則を確かめない（前の版の規則で保存したバックアップも開けるように）
- 古い正しいバックアップと差し替えられた場合は見分けられない。パスワードを知らない人は正しいファイルを作れないため、想定する脅威の外とした
- 見積もりの辞書は主に英語で、日本語をローマ字にした言葉や人名には弱いことがある。釣りや魚の名前などを辞書に足しているが、見積もりは強さを保証するものではない
