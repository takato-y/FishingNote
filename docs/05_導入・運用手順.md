## 1. 導入（開発の環境）

### 1.1 必要なもの

| 項目 | 内容 |
|---|---|
| パソコン | Windows（ビルドは `gradlew.bat` で行う）。CI は Linux（ubuntu-latest）で `./gradlew` を使う |
| 開発ツール | Android Studio、JDK 17、Android SDK（compileSdk・targetSdk 36） |
| 動作確認の端末 | Android 8.0（API 26）以上のエミュレータか実機。確認に使う環境は Pixel 8・API 36 のエミュレータ。地図アプリへの受け渡しと署名の確認を試す場合は、Google の入ったイメージ（Google Play か Google APIs）を使う |
| ネットワーク | ビルドのときにライブラリを取得するために使う。アプリ自身は通信しない |

### 1.2 取得とビルド

1. リポジトリを取得し、Android Studio で開く（Gradle の同期が終わるまで待つ）
2. コマンドでビルドする場合は、リポジトリの直下で次を実行する

   ```
   gradlew.bat assembleDebug
   ```

3. `app/build/outputs/apk/debug/app-debug.apk` ができれば成功である

### 1.3 端末に入れる

1. エミュレータを起動するか、実機を USB でつなぐ（実機は開発者向けオプションの USB デバッグをオンにする）
2. 次を実行する

   ```
   gradlew.bat installDebug
   ```

3. 端末のアプリの一覧に「釣りノート」が出て、起動すると下に5つのタブ（道具・セット・準備・記録・釣り場）が出れば成功である

### 1.4 見本データを入れる

画面を確かめるときは、架空の見本データを入れてから操作する。今のデータは見本データに置き換わる。

1. アプリとテスト用のアプリを端末に入れる

   ```
   gradlew.bat installDebug installDebugAndroidTest
   ```

2. 見本データを入れる

   ```
   adb shell am instrument -w -e class com.example.fishingnote.SampleDataSeeder -e seed true com.example.fishingnote.test/androidx.test.runner.AndroidJUnitRunner
   ```

3. 最後に `OK (1 test)` と出れば成功である。道具の画面に「アジングロッド 6.4ft」など、釣り場の画面に「見本海岸」「見本漁港 北堤防」が出る

### 1.5 テスト

| 種類 | コマンド | 注意 |
|---|---|---|
| 単体テスト | `gradlew.bat testDebugUnitTest` | パソコンだけで動く |
| 端末上のテスト | `gradlew.bat connectedDebugAndroidTest` | 実行すると、つないだ端末のアプリのデータが消える。普段使いの端末では実行しない。実行した後に画面を確かめる場合は、1.4 で見本データを入れ直す |

テストの内容は [テスト仕様書](04_テスト仕様書.md) に示す。

## 2. 日々の使い方（利用者）

| 場面 | 操作 |
|---|---|
| 道具をそろえる | 「道具」タブの「道具を追加」で登録する。ラインは巻き替えた日と知らせる日数を入れておくと、日数を超えたときに「巻き替え時期」と出る |
| 釣具店で | 「道具」タブで検索し、持っている物を確かめる。「残り少ない」「欲しい物」で絞り込める |
| 出発前 | 「セット」タブで「このセットで準備する」を押し、「準備」タブのチェックリストで持ち物を確かめる |
| 釣り場で | 「記録」タブの魚のボタンを、釣れるたびに押す。押し間違えたら、すぐ上の「元に戻す」を押す |
| 釣り場を探す | 「釣り場」タブで探す語（「釣り公園」「漁港」など）を押すと、おおよその現在地を付けて地図アプリで探す。気に入った場所は「釣り場を保存」で残す |

アプリ自身は通信しない。地図アプリ・検索のアプリ・利用者が選んだ保存先へ情報が渡るのは、利用者が操作したときだけである（[要件定義書](01_要件定義.md) REQ-021）。

## 3. バックアップと戻し方（利用者）

データは端末の中だけにあり、Android の自動バックアップと機種変更の引っ越しの対象から外している（REQ-022）。端末の故障・紛失・機種変更に備えるには、利用者が自分でバックアップを保存する。

### 3.1 保存する

1. 「道具」タブの右上のメニューから「バックアップを保存（機種変更・紛失に備える）」を選ぶ（最後の保存から30日を超えた・一度も無いときは、道具の一覧の上に保存の勧めも出る）
2. 「パスワードで守る」はオンのままにする（オフにすると、誰でも読める `.json` で保存される）
3. 「パスワードを作ってもらう（おすすめ）」を押し、「パスワードを表示する」で表示して、紙などに書き写す。書いた紙はバックアップのファイルと別の場所にしまう
4. 「保存先を選ぶ」を押し、端末のフォルダかクラウドの保存場所を選ぶ。パスワードで守った物は `.fnbk` で保存される

パスワードを忘れると、そのバックアップは戻せない。前の版（0.5.x 以前）で保存した `.json` は誰でも読める形のままなので、不要なら保存先から消す。

### 3.2 戻す

1. 新しい端末にアプリを入れ、「道具」タブの右上のメニューから「バックアップから戻す」を選ぶ
2. バックアップのファイルを選び、パスワードを入れる
3. 中身の件数を確かめて置き換える。今のデータはすべて置き換わる。読み込みに失敗したときは、今のデータは変わらない

「パスワードが違うか、ファイルが壊れています」と出た場合は、パスワードの打ち間違い（大文字と小文字・記号）を確かめる。

## 4. 保守

### 4.1 変更後の確認

変更したら、次をすべて行う。

| 順 | 確認 | コマンド・方法 | 合格の条件 |
|---|---|---|---|
| 1 | 単体テスト | `gradlew.bat testDebugUnitTest` | 全件合格 |
| 2 | テスト仕様書の一覧 | `python3 scripts/update_test_spec.py --check` | 「最新です」と出る。テストを足した・名前を変えた場合は、スクリプトの `TESTS` に説明を足し、`--check` を付けずに実行して作り直す |
| 3 | ビルド | `gradlew.bat assembleDebug` | `app-debug.apk` ができる |
| 4 | 端末上のテスト | `gradlew.bat connectedDebugAndroidTest`（エミュレータで実行） | 全件合格（条件を満たさない物は「スキップ」） |
| 5 | 画面 | 1.4 で見本データを入れ、エミュレータで操作する | [テスト仕様書](04_テスト仕様書.md) 4章の項目が満たされる |

1〜3 は、main への push とプルリクエストのたびに GitHub Actions でも実行される。4・5 は手元の環境で行う。

### 4.2 よくある変更

| 変更 | 直す場所 | 確認で特に見ること |
|---|---|---|
| 判定・集計の決まり | `app/src/main/java/.../domain/Rules.kt` | `RulesTest` |
| データベースの表 | `data` の Entity と DAO。表の構造の控えは `app/schemas` に出る | `RepositoryTest`、バックアップの書き出しと読み込み（`Backup`）の検査も合わせて直す |
| バックアップの暗号化・パスワードの決まり | `data/BackupCrypto.kt` | `BackupCryptoTest`、端末上の `RepositoryTest` と `PasswordCheckTimingTest`。[設計メモ](設計メモ.md) 5章の決まりを崩さない |
| 画面の文言・配置 | `ui` の各画面 | 押した結果で上の物の位置を動かさない（[ADR-0004](adr/0004-押した結果で画面の上の物の位置を動かさない.md)） |

### 4.3 ライブラリの更新

1. `gradle/libs.versions.toml` の版を上げ、4.1 の確認をすべて行う
2. Compose（`composeBom`）の版を上げたときは、パスワードの窓の入力欄を長押しして、文字のメニューに「コピー」「切り取り」が出ないことを確かめ直す（文字のメニューの絞り込みは、Compose の新しい文字のメニューが前提のため。[設計メモ](設計メモ.md) 6章）
3. パスワードの強さの見積もり（`zxcvbn`）の版を上げたときは、`BackupCryptoTest` と、端末上の `PasswordCheckTimingTest`（判定が1秒未満で終わるか）を確かめる

### 4.4 ライブラリを足す

1. `gradle/libs.versions.toml` と `app/build.gradle.kts` に足す
2. `app/src/main/java/.../ui/common/About.kt` のライブラリの一覧に、名前・権利者・ライセンスを足す。Apache License 2.0 のライブラリは、置いてある全文（`license_apache_2_0.txt`）を使う。それ以外のライセンス（MIT License を含む）は、ライブラリごとに著作権の表示を含む全文を `app/src/main/res/raw/license_*.txt` に置く（例：`license_zxcvbn4j.txt`・`license_zxcvbn_dropbox.txt`）
3. README の「使っている外部ライブラリ」を直す
4. インターネットにつながる仕組みを持つライブラリは足さない（アプリ自身は通信しない。[ADR-0002](adr/0002-インターネットの権限を持たずネット検索はブラウザに渡す.md)）

### 4.5 Google マップの証明書の値を足す

現在地や釣り場を渡す先の Google マップは、署名の証明書（SHA-256）で確かめている。値は `ui/common/Common.kt` の `GOOGLE_MAPS_CERT_SHA256` にある。
Google が鍵を更新すると、Google マップが入っている端末でも、渡すアプリを毎回選ぶ画面が出るようになる（使えなくはならない）。そのときは次を行う。

1. Google マップの入った端末で、Google マップの APK の署名の証明書の SHA-256 を取り出す（例：`adb shell pm path com.google.android.apps.maps` で場所を調べて `adb pull` し、Android SDK の `apksigner verify --print-certs` で表示する）
2. `Common.kt` の判定に新しい値を足す。今の判定（`isGenuineGoogleMaps`）は値を1つだけ受け取るため、古い版の Google マップが入った端末も考え、どちらかの値に合えば信用する形に直す（置き換えると、古い版の端末で選択画面が出るようになる）
3. 端末上の `SignatureTest.genuine_google_maps_is_trusted` を、Google の入ったエミュレータで実行し、合格することを確かめる

### 4.6 プライバシーポリシーを直す

1. 原稿は `docs/プライバシーポリシー.md` の1つだけである。アプリの中の本文は、ビルドのときにこの原稿から作られる（[ADR-0005](adr/0005-プライバシーポリシーは1つの原稿からビルド時に作る.md)）。アプリの中の文を直接直さない
2. 原稿は、題名（`#`）・見出し（`##`）・本文・箇条書き（`- `）・表だけで書く。`###`・`**`・リンクなどを使うと、単体テストの `PrivacyPolicyTest` が落ちる
3. `gradlew.bat testDebugUnitTest` を実行して `PrivacyPolicyTest` が合格することを確かめ、アプリの「このアプリについて」で表示を確かめる
4. 公開している文（ストアに載せる URL の文）も同じ原稿から作り直す

### 4.7 配布用のビルドの前に

配布用のビルドを名指しで作るとき（`assembleRelease`・`bundleRelease`・`packageRelease`・`installRelease`）は、`checkReleaseReady` が次の場合にビルドを止める。いつもの `build`・`assemble` では止めない。

| 止まる理由 | 対処 |
|---|---|
| プライバシーポリシーの原稿に【…】の形の未記入の欄が残っている | 欄を埋める |
| パッケージ名が `com.example` で始まっている | 配布用のパッケージ名を決めて直す |

あわせて、[設計メモ](設計メモ.md) 6章の残っている課題（暗号化の第三者の点検、依存のハッシュの照合、法律の専門家の確認など）を配布前に判断する。

## 5. 運用管理

### 5.1 定期点検

| 頻度 | 点検 | 方法 |
|---|---|---|
| 月1回 | ライブラリ・Android Gradle Plugin・Compose の更新の有無 | Android Studio の更新の知らせ、`gradle/libs.versions.toml` の版。上げる場合は 4.3 |
| 版を出すとき | 4.1 の確認がすべて合格しているか | GitHub Actions の結果と、手元の端末上のテスト・画面の確認 |
| 版を出すとき | 4.7 の配布前の検査 | `checkReleaseReady` が止めないこと |

### 5.2 資格情報・鍵

アプリは API キー・ログインの情報を持たない。バックアップの暗号化の鍵は、利用者のパスワードからその都度作り、アプリには残さない。配布用の署名の鍵は、リポジトリに置かない。

### 5.3 困ったとき

障害の切り分けと対処は、[障害対応手順書](06_障害対応手順書.md) に示す。

### 5.4 連絡体制

このアプリは個人の試作で、配布していない。このため、問い合わせの窓口と連絡先は置いていない。配布する場合は、次の役割の分け方をもとに、連絡の体制と連絡先を決める。

| 役割 | 受け持つこと |
|---|---|
| 利用者 | アプリを使う。想定と違う動きに気づいたら、問い合わせ先へ伝える |
| 問い合わせの窓口 | 利用者からの問い合わせを受け、障害対応手順書に沿って切り分ける。直らなければ保守担当者へ連絡する |
| 保守担当者 | 原因を調べ、必要ならソースを直して新しい版を出す |

連絡するときは、端末の機種と Android の版、アプリの版（「このアプリについて」に出る）、起きたことと操作の順をそろえる。バックアップのファイルとパスワードは、問い合わせで受け取らない（中身が利用者の記録のため）。
