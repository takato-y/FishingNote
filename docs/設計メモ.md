# 釣り道具ノート 設計メモ

アプリの正式な名前は「釣り道具ノート」。ホーム画面のアイコンの下には、切れずに収まる「釣りノート」を出す。
アイコンは海の青の地に白い魚とチェックの印（道具の確認と釣果の記録）。Android 13 以降のテーマアイコン用に、目と印をくり抜いた単色版を持つ。

## 1. 目的

釣りをする人が、道具の管理・出発前の準備・釣行の記録を1つのアプリで行えるようにする。
ログインなしで、データは端末の中だけに保存する。アプリ自身は通信しない（インターネットの権限を持たない）。
ただし次の3つでは、利用者の操作でアプリの外へ情報が渡る。

- 釣り場探し：検索語や保存した場所を、地図アプリに渡す。近くを探すときは、おおよその現在地（座標）も渡す
- 道具の「ネットで調べる」：入れたメーカー・商品名と道具の名前を、検索のアプリ（無ければブラウザで Google の検索）に渡す。画面に「言葉は検索サイトに送られます」と書く。検索語が http/https で始まるときは、そのサイトを開かず、検索サイトの検索として開く
- バックアップ：利用者が選んだ保存先（クラウドの場合もある）に、釣り場を含む全データを書き出す。保存するときに「パスワードで守る」を選べ、最初はオンにしておく（オンなら中身は暗号化され、パスワードを知らない人は読めない。オフなら誰でも読める JSON になることを、その場で知らせる）

## 2. 利用者の困りごとと機能の対応

| 困りごと | 機能 |
|---|---|
| 釣具店で、持っている道具を思い出せずに二重に買う | 道具の検索。欲しい物と、残りが少ない消耗品の一覧 |
| ラインの号数・長さ・巻き替え日を忘れる | 道具ごとの仕様の記録。巻き替えてからの日数の表示 |
| 釣りの種類ごとに道具をそろえるのが手間で、忘れ物をする | タックルセット。セットといつもの持ち物から、チェックリストを作る |
| 釣りの最中の記録が面倒 | 日付は今日を自動で入れ、場所と魚の種類は前の入力から選ぶ |
| ログインできずにデータを失う。釣り場を知られたくない | ログインなし。端末の中だけに保存し、ファイルに書き出してバックアップする |

ラインの交換時期は、釣り方や保管の状態で変わり、一律の目安を決められない。
そのため、知らせるまでの日数は利用者が道具ごとに決める（空欄なら知らせない）。

## 3. 画面

下のタブで5つの画面を切り替える。釣りの最中（片手・濡れた手・手袋）でも押せるよう、次の決まりにする。

- 押す対象は 56dp 以上（選択肢のチップも含む。チップ同士の間隔は 12dp）、主なボタンは高さ 60dp、ワンタップ記録のボタンは 76dp
- 押した結果で、画面の上の物の位置を動かさない。続けて押したとき、指の下に別の物が来て押し間違えるため
  - 持ち物チェックリストは、画面を開いたときの「まだの物が上」の並びで固定し、チェックしても行は動かさない（済みが下へまとまるのは次に開いたとき）
  - ワンタップ記録の魚のボタンの並びは、画面を開いたときの並びで固定する
  - ワンタップ記録の「元に戻す」は、魚のボタンのすぐ上の高さを固定した行に出す（画面下のお知らせにすると「ほかの魚」を隠すため）
- 文字は標準より一段大きくする（本文 18sp）
- 消す・減らす操作は、その場で取り消せるようにする。1件単位の軽い操作（数を減らす・チェックリストから外す・いつもの持ち物を消す）は「元に戻す」を出し、続けて外した分はまとめて戻す。道具・セット・記録・釣り場の削除は、関係するデータも消えるため確認ダイアログを出す。チェックリストの削除は「編集」中だけ出す
- 名前は40文字、メモは1000文字までにする。数は0〜9999、巻き替えの目安は3650日まで、魚の大きさは500cmまで
- 編集画面の保存ボタンは下端に固定し、変更したまま戻るときは確認する
- 色は白いカードと海の青を基本にし、意味を持たせる色は「注意（赤）」と「欲しい物（橙）」だけにする

| タブ | 画面 | 主な操作 |
|---|---|---|
| 道具 | 道具の一覧 | 検索、絞り込み（すべて・残りが少ない・欲しい物・巻き替え時期）、消耗品の数の増減 |
| セット | タックルセットの一覧 | セットの作成と編集、「このセットで準備する」 |
| 準備 | 持ち物チェックリスト | チェック、セットから作り直す、項目の追加、いつもの持ち物の編集 |
| 記録 | 釣行の記録と集計 | 「釣れたら押す」（魚のボタンを押すたびに今日の記録へ1匹足す）、今年の釣行回数・釣れた数・よく釣れた魚・セットごとの釣果、詳しい記録の追加 |
| 釣り場 | 釣り場探しとマイ釣り場 | 「釣り公園」「漁港」などを押して、地図アプリで現在地の近くを検索する。気に入った場所の保存と、地図での表示 |

釣り場探しは、地図アプリ（Google マップ）に検索語を渡して表示する。アプリの中に地図は持たない。
理由：地図を埋め込むには API キーと支払いの設定が要り、無料の地図部品（osmdroid）は開発が終わっているため。
近くを探すときは、アプリがおおよその現在地（ACCESS_COARSE_LOCATION）を1回だけ取り、座標を付けて地図アプリに渡す。
理由：座標を付けない検索（geo:0,0）では、地図アプリが現在地の近くを探すとは限らない（試したところ、日本全体を表示して遠い候補を出した）。
権限は探すボタンを初めて押したときに求める。現在地は保存しない。現在地は、使える取り方（fused・network・GPS）すべてに同時に問い合わせ、最初に届いた位置を使う（おおよその位置の権限では省電力の取り方になり、Wi-Fi の無い海辺では取れないことがあるため）。
権限を断られた・位置情報がオフ・10秒以内に取れない場合は、座標なしで地図アプリに任せ、理由を分けて表示する（権限がオフのときは設定画面を開く操作を添える）。
GPS を併用できるのは API 31 以降。API 30 以前は、おおよその位置の権限では Wi-Fi・基地局だけを使う。
前に取れた位置を使うのは2分以内のものだけで、新しさは端末の時計ではなく起動からの経過時間で比べる。待っている間に別のアプリへ移った場合は、地図を開かない。
座標を渡す先は Google マップに絞る（package を指定し、さらに署名の証明書が Google の物かを確かめる。名前だけで信用すると、Google マップの無い端末で同じ名前を名乗る別のアプリに渡してしまうため）。証明書の値は、端末に入っている Google マップから取り出した SHA-256。合わない場合（鍵の更新・別の鍵で署名された版など）は、渡す先を毎回選んでもらう側に倒れるだけで、使えなくはならない。入っていない端末では既定のアプリに任せず、毎回アプリの選択画面を出す（geo: を受け取れると名乗る別のアプリに、黙って現在地を渡さないため）。画面の説明にも、入っていない端末では選んだ地図アプリに渡すこと、渡した後の扱いは地図アプリの設定によることを書く。
保存した釣り場（緯度経度を含むことがある）を地図で開くときも、同じく Google マップに絞り、入っていなければ毎回アプリを選んでもらう。
渡した後の扱いは地図アプリ側による（検索履歴に残ることがある）。画面の「このアプリには保存しません」は、このアプリについての説明である。
釣り禁止・立入禁止の場所があるため、画面に「現地の表示に従う」旨を出す。

道具・セット・記録の編集は、一覧から開く別の画面で行う。
バックアップの書き出しと読み込みは、道具の画面の右上のメニューから行う。
一覧の画面の追加ボタンは、向きによらず上のバーに文字付きで置く（右下に浮かせると、一覧の行の「＋」（数を増やす）や「地図」のボタンに重なり、押し間違えるため）。
道具の一覧では、検索欄と絞り込みも一覧と一緒にスクロールする（上に固定すると、横向きで道具が1行しか見えないため）。
道具の登録の「メーカー・商品名」は、途中まで入れると候補を出す（全部を手で打たなくて済むように）。候補は最大6件で、前に登録した値（新しい順）を先に、主な釣り具メーカーの名前を後に並べ、それぞれの中で入れた言葉で始まる物を先にする（前に登録した値が6件当たれば、メーカー名は出ない）。文字の比べ方は一覧の検索と同じ（大文字と小文字・全角と半角・ひらがなとカタカナを区別しない）だが、語に分けず、入れた文字列のまま含むかで見る。メーカー名の一覧は名前だけで、商品の型番や仕様は持たない（古くなるため）。商品の詳しい情報は「ネットで調べる」で探し、利用者が入れる
  - ネットの商品検索の仕組み（ショッピングサイトの商品検索）をアプリから直接使う形は採らない。アプリが通信するようになり、サービスへの登録と ID の埋め込みが要るため。ブラウザの検索なら、登録も ID も要らず、アプリは通信しないままにできる
釣り場の画面は、保存した釣り場が1件以上あれば、それを「近くを探す」より上に出す。
ワンタップ記録で今日の記録を新しく作るときは、前回使ったセットを入れる（「セットごとの釣果」がすべて「セットなし」に集まらないように）。
ワンタップ記録の取り消しで釣行ごと消すのは、ワンタップで作った釣行で、場所・メモが空・セットが自動で入れたままの物だけ（利用者が先に作った釣行は、空でも残す）。バックアップを読み込んだ後は、読み込む前の「元に戻す」を効かなくする。
画面を回しても、ワンタップ記録の「元に戻す」と持ち物チェックリストの並びは残す（タブを離れたときにだけ並べ直す）。
道具の一覧では、数の増減ボタンを名前の下の行に置く（名前の横に置くと、名前が語の途中で折り返すため）。
記録の画面では、今日の記録があれば「今日の記録に場所・大きさを書き足す」から、その記録を開ける。「ほかの魚」では、前に記録した魚を押すだけで足せる。
セットの一覧は名前順のため、新しく作ったセットが見ている位置より上に入ったときは、そのセットまで送る。

## 4. データ

| 表 | 内容 |
|---|---|
| gear | 道具。名前・種類・メーカー・仕様・数・知らせる数・持っているか（欲しい物か）・巻き替え日・知らせる日数・メモ |
| tackle_set / set_gear | タックルセットと、セットに入れた道具 |
| basic_item | いつもの持ち物（ライフジャケット・プライヤーなど） |
| checklist_item | 今回の持ち物チェックリスト |
| trip / catch_entry | 釣行（日付・場所・使ったセット・メモ）と、釣れた魚（種類・大きさ・数） |
| spot | マイ釣り場（名前・地図で探すときの住所や緯度経度・メモ） |

## 5. 構成

- 画面：Jetpack Compose（Material 3）。画面ごとに ViewModel を置き、状態は StateFlow で渡す
- 保存：Room。種類は文字で、日付は日数（epoch day）で保存する
- 判定：巻き替え時期・残りの少なさ・集計・チェックリストの作成は、画面から切り離した関数（domain/Rules.kt）にまとめ、単体テストで確かめる
- バックアップ：全部の表を JSON にして書き出す。読み込みは全件の置き換えで、実行前に確認する
  - パスワードで守る場合（data/BackupCrypto.kt）：鍵は端末の中（Android の鍵保管庫）に置かず、利用者のパスワードから作る。バックアップは機種変更や紛失のときに別の端末へ戻すための物で、端末の中の鍵では端末と一緒に失われるため
    - 鍵の作り方は PBKDF2（HMAC-SHA256、繰り返し 600,000 回、毎回ランダムな16バイトの塩）、暗号は AES-256-GCM。パスワードが違う物と改ざんされた物は、復号の時点で止まる。形式・版・繰り返し回数も認証の対象に含める
    - 読み込むときは、繰り返し回数が 100,000〜2,000,000 の物だけ受け付ける（極端な値で読み込みが終わらなくなるのを防ぐ）
    - パスワードは半角の英数字と記号だけで12文字以上。よく使われる物・よくある言葉（password・qwerty・fishing・tsuri など）に数字や記号を足した・文字を置き換えた（P@ssw0rd など）・くり返しただけの物・使っている文字（異なる文字の数）が5種類未満の物・数字だけ・同じ文字だけ・並んだ文字だけ（上り・下り）・4文字以下の並びのくり返しの物は使えない。2回入れて確かめる
    - そのうえで、強さを見積もる仕組み（zxcvbn の Java 版。辞書の言葉・人名・日付・キーボードの並び・言葉のつなぎ合わせなどから、推測に要る回数を見積もる）で、一番上の段階（推測に 10^10 回以上かかる見込み）に届かない物は断る。アプリでよく使われそうな言葉（釣り・魚の名前など）も見積もりの辞書に足す
      - バックアップは手に入れた人が端末の外で時間をかけて試せるため、一番上の段階を求める
      - 見積もれなかったとき（辞書を読めない等）は、自分で決めたパスワードを断る（確かめずに通さない）
      - 見積もりを使うのは、自分で決めたパスワードを画面で受け付けるかの判定だけ。アプリが作ったパスワード（ランダムな約93ビット）と、暗号化の直前の確認は規則だけで見る（見積もりが使えない端末でも、作ったパスワードで保存できるように）。作り直しは回数を決めて止める
      - 保存を押したときは、いま入っているパスワードに対する判定が済んでいるときだけ進む（打った直後に押して、古い判定のまま進まないように）。暗号化に入る道は、保存の確認の「保存先を選ぶ」の1つだけで、押した時点の値（判定した値と同じ物）をそのまま鍵の計算まで渡す。暗号化の直前は規則だけで見るので、別の入口を足すときは、画面と同じ判定（規則と見積もり）を必ず通すこと
      - 作った鍵の値は、鍵を作る部品が返す鍵と SecretKeySpec の中に写しが残り、消せない（取り出した配列は消す）
      - 作ったパスワードかどうかは、パスワードの欄が作った値のままかで決める（確認の欄を打ち直しても作った物のまま。パスワードの欄を書き換えたら自分で決めた物として見積もりも行う）
      - 判定は画面のスレッドの外で、打ち終わってから行う（見積もりに時間がかかる端末で入力が引っかからないように）。判定が済むまでは保存に進めない。断る理由は、その欄のすぐ下に出す（確認の窓の下の方に出すと、スクロールの外に隠れて気づけないため）
      - 見積もりの部品は、複数のスレッドから同時に使わない（1つずつ順に行う）
      - 見積もりには使い捨ての写しを渡し、終わったら写しを消す（見積もりの後始末は渡した入れ物そのものを0で埋めるため、鍵を作る配列を渡すとパスワードが消えて別の鍵になる。テストで確かめる）
      - 見積もりの辞書は、保存の確認を開いたときに画面の外で読み込んでおく
      - 12文字以上にする理由：人が考えたパスワードは、見た目の長さほど推測されにくくない。ファイルを手に入れた人は、時間をかけて候補を試せる（繰り返し回数を増やしても、弱いパスワードは補えない）
    - 保存の画面では「パスワードを作ってもらう（おすすめ）」を先に出す。人が考えたパスワードは、規則で断れる物を避けても推測されることがあるため。自分で決めることもできるが、見積もりは強さを保証するものではないことを画面に書く
      - 作るパスワードは、4文字ずつ4組をハイフンでつないだ19文字（見間違えやすい 0・O・1・l・I を除いた57種類の文字を16個。約93ビット）
      - 作った物も最初は伏せる。「パスワードを表示する」を押して紙などに書き写すよう、また書いた紙はバックアップのファイルと別の場所にしまうよう知らせる
    - 保存と読み込みの両方で、パスワードを表示するかを選べる（長いパスワードを伏せたまま入れると打ち間違えやすいため。最初は伏せる）。次のときに伏せ直す：アプリを離れたとき、確認の窓が操作の対象でなくなったとき（画面分割でほかのアプリに触れた・通知を引き出した等）、表示から1分たったとき
    - パスワードを扱う確認の窓（ダイアログの窓だけ）に FLAG_SECURE を付ける。エミュレータで確かめたのは、保存の窓で画面の撮影が黒くなることだけ（「最近使ったアプリ」の一覧での表示は確かめていない）
    - パスワードの入力欄の文字のメニューは、貼り付け・全選択・自動入力だけにする（コピー・切り取り・読み上げ・ほかのアプリへ渡す項目を外す）。クリップボードへの写しの機能も用意しない。そのうえで、確認の窓の中ではクリップボードを「書き込めない物」に差し替える。コピーはメニュー・キーボード（Ctrl+C・Ctrl+Insert・専用のコピーキー）・入力方式からの要求のどれも最後はクリップボードへ書くので、経路ごとに止めるのではなく書き込み先で止める（貼り付けは元のクリップボードから読む）。切り取りは、写らなくても欄から文字が消えるので、キーボードの操作（Ctrl+X・Shift+Delete・専用の切り取りキー）でも止める
    - 読み込みでは、パスワードの規則を確かめない（前の版の規則で保存したバックアップも開けるように。テストで確かめる）
      - 半角に限る理由：全角や濁点の分かれた形などは、端末の入力の設定で見た目が同じでも別の文字になり、機種変更の後に戻せなくなるため。どの端末でも同じ鍵になることは、別の実装（Python）で作った見本と同じ結果になるかを、パソコンと端末の両方のテストで確かめる
    - パスワードは画面の回転で保存される領域には置かない。受け渡しの配列は使い終わったら消す（画面の入力欄の文字そのものは、仕組み上すぐには消せない）
    - 保存の画面には「忘れると戻せないこと」を書く
    - 開けないときは「パスワードが違うか、ファイルが壊れています」と出す（どちらかを区別できないため）
    - パスワードで守られていないファイルを読み込むときは、置き換えの確認に「このファイルはパスワードで守られていません」と出す（中身を差し替えられていても気づけないため）
    - 保存は画面ではなく ViewModel で動かし、書き始めたら最後まで終える（保存の途中で画面を回しても、空のファイルが残らず、結果を必ず知らせる。ただし保存の途中でアプリそのものを終了させられた場合は、空のファイルが残ることがある）。保存している間は、保存のメニューを押せない
    - 失敗したときに消すのは、書き込みを始めた後のファイルと、大きさが0のファイルだけ（書き込みを始める前の失敗では、中身のあるファイルは消さない）。暗号文はメモリの中で作り終えてから保存先を開く
    - 保存先を選んでいる間にアプリが終了させられると、預かったパスワードは失われる。そのときは空のファイルを消し、もう一度保存するよう知らせる
    - 端末（エミュレータ）での所要時間は、暗号化・復号ともに約2秒。性能の低い端末では長くなるため、保存中と確かめ中はその旨を表示する
    - ファイルは .fnbk（中身は6行のテキスト）。暗号化していない物は .json
- 外から入る値の検査
  - 地図アプリの共有：2000文字を超える物は受け取らない（途中で切ると別の場所になるため）。見えない文字（ゼロ幅・向きを変える制御文字）は取り除く。地図の URL は、https・決まったホスト・決まったパスの物だけを受け付け、「..」やエンコードした区切りを含むパスは受け付けない
  - バックアップの読み込み：5MB を超えるファイルは読まない。表ごとの件数・ID の重複・文字の長さ・数の範囲（数 0〜9999、魚の数 0〜99999、大きさ 0〜500cm、日数 0〜3650、並び順 0〜1000000）・日付（1900〜2100年）を確かめ、外れていたら何も変えずに止める。整数は丸めずに読む（範囲外の数・小数・文字で書いた数は止める。丸めると 4294967297 が 1 になる等、範囲内に見えてしまうため）
  - バックアップの書き出し：書く前に、読み込みと同じ上限と検査を通す（書き出せたのに読み戻せないバックアップを作らないため）。画面の「＋」「－」やワンタップ記録で増減する数も、読み込みの範囲（道具の数 0〜9999、魚の数 0〜99999）に収める
- Android 標準の自動バックアップと、新しい機種への引っ越し（端末間の移行）は止める。Android 11 以前は android:allowBackup="false"、Android 12 以降は data_extraction_rules.xml で、cloud-backup と device-transfer の両方から全領域を除外する（allowBackup="false" だけでは、機種によって端末間の移行が止まらないため）。データの移し替えは、上のバックアップで行う

## 6. 残っている課題

- Google マップの証明書の値は、エミュレータ（Pixel 8・API 36）に入っている版の1つから取った。Google が鍵を更新した場合は選択画面が出るようになるので、そのときに値を足す
- 画面の操作（並びが動かない・ボタンが重ならない等）は、エミュレータで目で確かめた。画面を操作する自動テストは無い
- 自分で決めたパスワードの強さは見積もりで判定しており、保証ではない。見積もりの辞書は主に英語で、日本語をローマ字にした言葉や人名には弱いことがある。求める段階（推測に 10^10 回以上）は、繰り返し 600,000 回の鍵の作り方と合わせて、1台の GPU で数日から十数日ほどの見込み（GPU の速さによる。要検証）。より強く求めるかは配布前に判断する
- パスワードを表示している間は、入力欄の文字がユーザー補助（読み上げなど）から読める。また、自動入力のアプリが保存を勧めることがある（実機では確かめていない）
- 消せるパスワードの写しは、アプリが持つ配列と見積もりの結果の中の物、作った鍵の元の配列だけ。入力欄の文字と、見積もりの部品の中で一時的に作られる文字列は、仕組み上すぐには消せない
- 使っている外部ライブラリのライセンスは、道具の画面のメニュー「このアプリについて（プライバシー・ライセンス）」に、全文とともに出す（一覧はリリース版の依存の一覧から作り、各ライブラリの公開情報（POM）のライセンス名で確かめた。ライブラリを足したら一覧も直す）。取り込むライブラリのファイルのハッシュの照合（Gradle の依存の検証）は、配布する前に入れる
- 文字のメニューの絞り込みは、Compose の新しい文字のメニュー（いまの版では既定で有効）が前提。Compose の版を上げたときは、表示中の長押しで「コピー」が出ないことを確かめ直す
- バックアップの暗号化は、2026-11-25 に、方式（鍵の作り方・暗号・ファイルの形式・読み込みの検査・パスワードの扱い）を文章にまとめ、開発者側で点検した（コードそのものは点検の対象外）。これは第三者による点検ではなく、第三者の監査は受けていない。配布する前に受けるか判断する
- 古い正しいバックアップと差し替えられた場合は見分けられない（パスワードを知らない人は正しいファイルを作れないため、想定する脅威の外とした）
- プライバシーポリシーの原稿は docs/プライバシーポリシー.md（下書き）。Google Play のデータセーフティの申告は、配布するときに作る。アプリの中では「このアプリについて」から同じ本文を読める（ビルドのときに原稿から作るので、ずれない）。配布用のビルドは、原稿の未記入の欄とパッケージ名が仮のままだと止まる（checkReleaseReady）。配布する前に、公開する URL・問い合わせ先の書き方（運営者名と連絡先を載せるか）・パッケージ名（com.example のまま）を決める。法律の専門家の確認は受けていない
